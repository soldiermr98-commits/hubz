# آزمون ایمن بارگذاری تصویر

این راهنما مخصوص توسعه‌دهنده و **فقط ماشین/کانتینر مستقل با دادهٔ ساختگی و دورریختنی** است. هیچ اسکریپت fixture، دیتابیس، کرون، کلید یا ترافیک واقعی را در آن قرار ندهید. نام `hhx_test_*` و localhost به‌تنهایی اثبات جدابودن سرور نیست. مسیرهای آزمایش را هرگز روی هاست عملیاتی یا کپی متصل به آن اجرا نکنید.

## تفاوت RC1 و RC2

بستهٔ `after-v2026.11.07.5-rc1` در PR شماره ۱۸ ادغام شده، اما به کد قبل از اصلاح بارگذاری تصویر پین است. **تغییرهای `MediaService.php` و `BusinessController.php` در RC1 نیستند.** این اصلاح‌ها در PR ۱۹ ادغام و در نامزد مستقل [RC2](../release-files/after-v2026.11.07.5-rc2/RAHNAMA-FA.md) گنجانده شده‌اند. RC2 از مبنای `.5` ساخته شده، نه به‌صورت وصله‌ای روی RC1؛ هیچ‌یک از دو ZIP را بی‌صدا تغییر ندهید. دستورهای HTTP زیر RC2 را در یک کپی ساختگی استخراج می‌کنند و فایل اجرایی را دستی جایگزین نمی‌کنند.

## رفتار و محدودیت نسخهٔ اصلاح‌شده

- ورودی واقعی JPEG/PNG/WebP به سه فایل واقعی WebP تبدیل و پیش از ثبت دیتابیس بازخوانی می‌شود؛ نبود قابلیت encode/decode WebP در GD به‌جای ذخیرهٔ JPEG با پسوند اشتباه، خطای روشن می‌دهد.
- افزونه‌های `gd` با WebP، `fileinfo`، `mbstring` و `PDO MySQL`، امکان نوشتن در uploads و جدول `media` از نوع InnoDB لازم‌اند. اندازهٔ آپلود حداکثر ۵ مگابایت، هر ضلع ۱۰۰ تا ۱۰٬۰۰۰ پیکسل و مساحت حداکثر ۱۶ میلیون پیکسل است؛ متن جایگزین حداکثر ۲۵۵ نویسهٔ UTF-8 است. محدودیت `upload_max_filesize`، `post_max_size` و حافظهٔ PHP ممکن است عملاً سخت‌گیرانه‌تر باشند. برآورد حافظه محافظه‌کارانه است و تضمین نمی‌کند در هر شرایطی حافظه کافی باشد.
- در خطای قابل‌کنترل پردازش/ثبت، فایل‌های ساخته‌شدهٔ همان درخواست حذف و تراکنش خود آن لغو می‌شود. اگر پاک‌سازی شکست بخورد پیام خطا داده می‌شود. در قطع غیرقابل‌گرفتن پردازش، فقدان دسترسی حذف یا نتیجهٔ نامشخص rollback/COMMIT، ممکن است فایل باقی بماند؛ در نتیجهٔ نامشخص تراکنش فایل‌ها عمداً حفظ می‌شوند تا رکوردی که شاید ثبت شده خراب نشود. پیش از تکرار درخواست، مدیر باید رکورد و فایل‌ها را بررسی کند؛ حذف گروهی خودکار توصیه نمی‌شود.
- نام‌های خروجی به‌صورت انحصاری ساخته می‌شوند تا برخورد تصادفی، فایل قبلی را بازنویسی یا حذف نکند. هیچ‌یک از این موارد معادل تأیید امنیت، پایداری زیر بار یا آمادگی هاست واقعی نیست.

## تست مستقل سرویس با GD و PDO ساختگی

در محیطی با PHP دارای GD/WebP، `mbstring`، `fileinfo` و کلاس PDO، از ریشهٔ شاخه اجرا کنید:

```bash
HHX_ALLOW_TEST_FIXTURES=1 php tests/media_service_synthetic_smoke.php
```

این تست فقط یک پوشهٔ تصادفی در دایرکتوری موقت می‌سازد، منبع PNG شفاف تولید می‌کند و PDO و منشأ آپلود را جعل می‌کند؛ دیتابیس واقعی و HTTP را تست نمی‌کند. مسیر موفق و شفافیت، برخورد نام، خطای درج، rollback نامشخص، تراکنش خارجی و COMMIT با نتیجهٔ نامشخص را بررسی می‌کند. در پایان تلاش می‌کند فقط فایل‌های خودش را پاک کند.

## تست HTTP و خطاهای تزریق‌شده

۱. یک دیتابیس خالی MySQL کاملاً جدا با نام `hhx_test_media` و کاربر **آزمایشی محدود** بسازید. جدول رسانهٔ fixture از نوع InnoDB است. فقط برای تست خطای درج، مجوز ایجاد/حذف trigger و جدول و پشتیبانی MyISAM برای نشانگر موقت آن در همین دیتابیس لازم است. سوکت نمونهٔ MySQL را در مسیر موقت قرار دهید؛ یک سرور واقعی را فقط به‌دلیل نام localhost یا نام تست انتخاب نکنید. نسخهٔ PHP دارای GD، PNG/JPEG/WebP، `fileinfo`، `mbstring` و `PDO MySQL` و Node.js نسخهٔ ۲۲ یا جدیدتر لازم است. هیچ پردازش دیگری نباید هم‌زمان در این پوشه یا دیتابیس بنویسد.

۲. از ریشهٔ مخزن، یک کپی کاملاً نو در زیر شاخهٔ موقت بسازید، RC2 را با آزمون overlay استخراج و فقط فایل‌های fixture را به آن کپی کنید. آزمون به اشیای Git پین‌شده در راهنمای ارتقا نیاز دارد:

```bash
ROOT="$PWD"
PARENT="$(mktemp -d)"
STAGE="$PARENT/site"
python3 tests/upgrade_candidate_overlay_smoke.py --candidate rc2 --stage "$STAGE"
mkdir -p "$STAGE/tests"
cp tests/setup_article_url_fixture.php tests/article_fixture_router.php tests/media_fault_fixture_router.php "$STAGE/tests/"
```

۳. `config/config.local.php` نشانگر ساختگی را فقط در همان کپی با پیکربندی نمونه و تنظیمات دیتابیس دورریختنی جایگزین کنید: `db.host` برابر `localhost`، `db.unix_socket` مسیر صریح سوکت موقت، `db.database` برابر `hhx_test_media`، نام کاربر و رمز صرفاً آزمایشی، `security.cookie_secure=false` برای HTTP محلی و `app.url=http://127.0.0.1:8091`. سندباکس پرداخت باید خاموش بماند؛ ارائه‌دهنده و cron واقعی را فعال نکنید. پیکربندی را در مخزن یا گفتگو ذخیره نکنید. سپس fixture کاربران/جدول‌های ساختگی را **فقط در دیتابیس خالی** اجرا کنید:

```bash
export HHX_ALLOW_TEST_FIXTURES=1
export HHX_TEST_STAGE_ROOT="$STAGE"
export HHX_TEST_CONFIG="$STAGE/config/config.local.php"
export HHX_TEST_PASSWORD='synthetic-only-password'
export HHX_TEST_NONCE='synthetic-media-only-nonce-2026'
export HHX_TEST_URL='http://127.0.0.1:8091'
php "$STAGE/tests/setup_article_url_fixture.php"
```

۴. با همان متغیرها، در ترمینالی جدا سرور PHP فقط روی loopback را اجرا کنید؛ آن را در دسترس شبکه نگذارید:

```bash
php -S 127.0.0.1:8091 -t "$STAGE/public_html" "$STAGE/tests/article_fixture_router.php"
```

در ترمینال اصلی و از ریشهٔ مخزن، بدون `HHX_TEST_MEDIA_FAULT` اجرا کنید:

```bash
unset HHX_TEST_MEDIA_FAULT
node tests/media_upload_http_smoke.mjs
php tests/media_database_fault_fixture.php
```

تست HTTP تصاویر ساختگی PNG/JPEG/WebP، اندازه و نوع خروجی، دسترسی مهمان/مدیر/نویسنده، CSRF، ورودی‌های نامعتبر و محدودیت ابعاد را بررسی می‌کند. تست دوم ابتدا مسیر موفق را دوباره اجرا می‌کند، سپس برای شکست واقعی درج در دیتابیس دورریختنی یک trigger و جدول نشانگر موقت ایجاد، اجرای trigger، تعداد سطر و حذف فایل را بررسی و در `finally` هر دو را پاک می‌کند؛ در قطع اجباری پردازش ممکن است باقی بمانند، بنابراین نمونهٔ DB را پس از آزمون معدوم کنید. تست‌ها به مسیر و تنظیمات همان کپی با nonce و digest مقیدند.

۵. سرور عادی را متوقف کنید. برای هر یک از خطاهای `no_webp`، `second_write` و `truncated_success` جداگانه، همان سرور loopback را با router تزریق خطا راه بیندازید و با همان مقدار در ترمینال اصلی تست کنید؛ این‌ها شبیه‌سازی سطح تابع‌اند، نه قطع واقعی دیسک یا تغییر GD هاست:

```bash
# در ترمینال سرور؛ برای هر حالت تکرار و پس از آن سرور را متوقف کنید
export HHX_TEST_MEDIA_FAULT=second_write
php -S 127.0.0.1:8091 -t "$STAGE/public_html" "$STAGE/tests/media_fault_fixture_router.php"

# در ترمینال آزمون، با همان مقدار و سایر متغیرهای بالا
export HHX_TEST_MEDIA_FAULT=second_write
node tests/media_upload_http_smoke.mjs
```

اگر یک PHP محلی و دورریختنی واقعاً بدون GD در دسترس دارید، سرور عادی fixture را با آن اجرا کنید و در ترمینال آزمون `HHX_TEST_MEDIA_FAULT=no_gd node tests/media_upload_http_smoke.mjs` بزنید؛ این مسیر باید با خطای مشخص و بدون فایل رد شود. این حالت را با router تزریق خطا راه نیندازید.

در پایان همهٔ سرورها و دیتابیس آزمایشی را متوقف کنید. نتایج این تست‌ها جای ارزیابی روی staging مشابه هاست، نسخه PHP و GD واقعی، مجوزها، بازیابی بکاپ یا بررسی مستقل امنیت و پرداخت را نمی‌گیرند.
