# بازتولید آزمون نامزد ارتقا پس از `.5`

این راهنما برای توسعه‌دهنده و **صرفاً محیط کاملاً دورریختنی و مستقل** است؛ روی هاست عملیاتی، روی کپی متصل به سرویس‌های واقعی یا روی دیتابیس دارای اطلاعات واقعی اجرا نشود. شرط نام `hhx_test_*` و `localhost` به‌تنهایی ثابت نمی‌کند یک سرور MySQL، آزمایشی و جدا از سرور واقعی است. cron، شبکهٔ ارائه‌دهندگان، پیام‌رسانی و سایر خروجی‌های واقعی را غیرفعال کنید. هیچ کلید یا اطلاعات شخصی در نمونه‌ها لازم نیست.

## بازسازی ZIP و بررسی آفلاین

از ریشهٔ مخزن، پس از اطمینان از وجود commit مبنای `3547693` و مقصد RC2 یعنی `17be5bb` و مقصد RC1 یعنی `543b0d6` در Git:

```bash
python3 tests/build_update_candidate_smoke.py
python3 scripts/build_update_candidate.py --candidate rc2
python3 tests/upgrade_candidate_overlay_smoke.py --candidate rc2
(cd release-files/after-v2026.11.07.5-rc2 && sha256sum -c SHA256SUMS.txt)
```

سازنده، کد اجرایی را از اشیای Git می‌خواند نه از فایل‌های تغییرکردهٔ محلی. RC2 یک تغییر تجمیعی **از مبنای `.5`** است، نه وصله‌ای برای RC1. آزمون overlay نصب کامل قدیمی و بسته‌های به‌روزرسانی را در پوشهٔ موقت بازسازی می‌کند؛ ۸۰ فایل مبنا، ۲۸ فایل RC2، ۹۶ فایل مقصد، فهرست‌های هش، محتوای ZIP، حفظ فایل‌های ساختگی و تفاوت دقیق دو فایل رسانه با RC1 را بررسی می‌کند. این فقط شبیه‌سازی مبنای مخزن است، نه کپی هاست کاربر.

سازنده فایل موجودِ متفاوت یا symlink را بازنویسی نمی‌کند و نوشتن در پوشهٔ نامزد دیگر را رد می‌کند؛ بازسازی یکسان نیز فایل موجود را تغییر نمی‌دهد. انتشار فایل جدید به hard link در همان فایل‌سیستم نیاز دارد تا فایل ناقص با نام نامزد دیده نشود؛ در صورت پشتیبانی‌نشدن، ساخت متوقف می‌شود و باید از فایل‌سیستم محلی مناسب استفاده کرد. نسخه‌های متفاوت Python/zlib ممکن است فشرده‌سازی و هش ZIP متفاوت بسازند. در صورت اختلاف، فایل منتشرشده را حذف یا تغییر ندهید؛ با `--output` یک پوشهٔ موقت **جدید** را مشخص و محتوای ZIP، CRC و مانیفست را مقایسه کنید. تست سازنده بازسازی هر دو نامزد و محافظت در برابر تعارض را بررسی می‌کند. برای بازتولید RC1 از `--candidate rc1` استفاده کنید؛ انتخاب پیش‌فرض سازنده و آزمون overlay برای سازگاری، همچنان RC1 است.

## آزمون دو مرحله‌ای دیتابیس

1. یک ماشین/کانتینر مستقل و بدون دادهٔ واقعی با PHP دارای `PDO MySQL` و `mbstring` و یک MySQL محلی راه بیندازید. یک دیتابیس **خالی و دورریختنی** با نامی مانند `hhx_test_upgrade_demo` و دسترسی محدود ایجاد کنید. نام، میزبان و مسیر Unix socket باید واقعاً مربوط به همان نمونهٔ جداگانه باشند.
2. از ریشهٔ مخزن، یک پوشهٔ جدید خارج از مخزن برای نصب ساختگی بسازید. نمونهٔ زیر خودِ پوشهٔ `site` را توسط آزمون می‌سازد؛ از مسیر قبلی یا واقعی استفاده نکنید:

   ```bash
   ROOT="$PWD"
   PARENT="$(mktemp -d)"
   STAGE="$PARENT/site"
   python3 tests/upgrade_candidate_overlay_smoke.py --candidate rc2 --baseline-only --stage "$STAGE"
   ```

   این حالت کد قدیم و دو fixture آزمایشی را نگه می‌دارد. فایل `config/config.local.php` در آن صرفاً نشانگر ساختگی است؛ آن را با پیکربندی **فقط همان دیتابیس موقت** جایگزین کنید. کلید `advertising_payments.experimental_sandbox` باید غایب یا بولی `false` باشد. مقادیر واقعی و کلیدهای واقعی به این محیط وارد نکنید.
3. با PHP محلی، مسیر مطلق پیکربندی ساختگی و یک رمز کاملاً ساختگی حداقل ۱۲ نویسه، متغیرهای زیر را تنظیم کنید؛ سپس fixture را اجرا کنید. رمز و تنظیمات واقعی را در فرمان، مستندات یا گفتگو قرار ندهید.

   ```bash
   export HHX_ALLOW_TEST_FIXTURES=1
   export HHX_TEST_CONFIG="$STAGE/config/config.local.php"
   export HHX_TEST_PASSWORD='synthetic-only-password'
   php "$STAGE/tests/setup_article_url_fixture.php"
   php "$STAGE/tests/upgrade_candidate_database_smoke.php" baseline
   ```

   فاز `baseline` با کد قدیم، مایگریشن‌های هدفمند `006` و `007` را اجرا می‌کند و محتوای منتشرشده و تنظیمات ساختگی می‌سازد؛ `003` عمداً ثبت نمی‌شود. fixture داده‌ها را commit می‌کند و دیتابیس باید خالی باشد.
4. پیش از استخراج، فهرست مبنا را از **ریشهٔ همان کپی آزمایشی** بررسی کنید. سپس دقیقاً ZIP تولیدشده را روی همان پوشه استخراج و مانیفست داخل آن را بررسی کنید:

   ```bash
   (cd "$STAGE" && sha256sum -c "$ROOT/release-files/after-v2026.11.07.5-rc2/BASELINE-SHA256.txt")
   (cd "$STAGE" && unzip -o "$ROOT/release-files/after-v2026.11.07.5-rc2/hamihub-update-after-v2026.11.07.5-rc2.zip")
   (cd "$STAGE" && sha256sum -c UPGRADE-RC-MANIFEST.txt)
   php "$STAGE/tests/upgrade_candidate_database_smoke.php" upgraded
   ```

   فاز دوم باید توقف اجرای عمومی هنگام غیبت `003`، اجرای هدفمند `008` تا `010`، اجرای دوباره بدون تغییر، حفظ محتوای قدیم و خاموش‌بودن سندباکس را بررسی کند. خطا را دور نزنید. این فرآیند عمداً فقط روی دادهٔ ساختگی است.
5. برای تست برخورد رسید، یک دیتابیس خالی و مستقل دیگر از همان نوع و پیکربندی ساختگی جداگانه بسازید. سپس فقط اسکریپت تست را به کپی به‌روزشده اضافه کنید و با مسیر مطلق تنظیمات دیتابیس جدید اجرا کنید:

   ```bash
   cp "$ROOT/tests/advertising_receipt_migration_smoke.php" "$STAGE/tests/"
   export HHX_TEST_CONFIG="$STAGE/config/config.conflict.php" # فقط پیکربندی دیتابیس خالیِ دوم
   php "$STAGE/tests/setup_article_url_fixture.php"
   php "$STAGE/tests/advertising_receipt_migration_smoke.php"
   ```

   آن تست تعارض ساختگی می‌سازد و فقط در fixture یک ثبت را ابطال می‌کند؛ این کار دستور رفع تعارض حسابداری واقعی نیست.

تست‌های HTTP و هم‌زمانی موجود در `tests/` نیاز به fixtureهای محافظت‌شده و دیتابیس‌های ساختگی جداگانه دارند؛ مستندات `ADVERTISING_FINANCE_FA.md` را ببینید. سرورهای موقت را پس از آزمون متوقف کنید. هیچ نتیجه‌ای از این آزمون‌ها، بازیابی بکاپ، امنیت، کارکرد روی هاست واقعی یا رفتار درگاه واقعی را به‌تنهایی تأیید نمی‌کند.

اصلاح آپلود در RC2 موجود است، اما در ZIP پین‌شدهٔ RC1 نیست. [راهنمای تست آپلود](MEDIA_UPLOAD_TEST_FA.md) کپی استخراج‌شدهٔ RC2 و محدودیت پوشش را توضیح می‌دهد؛ نتیجهٔ محلی جای آزمایش روی staging مشابه هاست را نمی‌گیرد.
